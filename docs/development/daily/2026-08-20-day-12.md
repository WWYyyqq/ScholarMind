## 2. 正式数据契约

新增：

- `evaluation/schemas/paper_review.schema.json`；
- `evaluation/schemas/paper_gold_question.schema.json`。

两份 Schema 使用 JSON Schema Draft 2020-12，严格限制 ID、题型、错误码、两轮
checks、修订、resolution、Gold 导出字段和 provenance。公开空模板同步升级为
`schema_version=1.0.0`、`annotation_spec_version=1.0`；冻结脚本移除仅供说明的
`template_notice` 后，会立即用正式 Review Schema 验证每个空记录。

Schema 负责稳定结构和字段类型，跨轮时间、决定一致性、来源回连和坐标计算等
跨字段规则由构建器验证，避免把复杂业务约束隐藏在难维护的 Schema 条件中。

## 3. Gold 构建器

新增 `scripts/build_gold_dataset.py`。输入是只读论文数据集和
`prepare_silver_review.py` 创建的私有复核工作区，输出仍留在该私有工作区：

```text
reviews/questions.review.jsonl
gold/questions.gold.jsonl
build_manifest.json
review_summary.md
```

核心验证顺序：

1. 重新计算 Silver、`source_checksums.sha256` 及其中每个冻结文件的 SHA-256；
2. 用正式 Schema 验证全部 Silver、Review 和最终 Gold；
3. 要求 Silver 与 Review 的 `question_id` 集合完全相等且 ID 唯一；
4. 检查 release-scoped `annotation_record_id`、来源 ID 和输入哈希；
5. 检查两轮决定、checks、错误码、修订、时间戳和复核协议；
6. 单人复核要求同一代号且两轮至少间隔 24 小时，双人复核要求代号不同；
7. 无分歧记录必须严格符合 `not_required` 规则，有分歧记录必须完成裁决；
8. `keep` 从 Silver 复制，`edit` 从 final revision 复制，`reject` 不导出；
9. 按 `documents/*.json` 的真实 text block 重算页码、阅读顺序、bbox 和归一化 bbox；
10. 要求规范化后的答案等于所选文本块原文，防止流畅但无证据的答案进入 Gold；
11. 同步派生 `gold_export`，记录输入/输出哈希、Commit、决定数和作品覆盖数；
12. 所有记录通过后才原子替换生成文件，避免半成品。

Gold ID 由 `gold_version + question_id` 确定性生成。重复构建同一 release 得到稳定
ID；更换 Gold 版本会得到不同 ID。已有聚合输出时默认拒绝覆盖，只有明确传入
`--replace-generated` 才允许重建生成物，单题 Review 文件不会被修改。

## 4. 隐私与泄漏边界

- GitHub 只保存 Schema、构建器、公开空模板、合成测试和聚合说明；
- 真实问题、答案、Evidence、Review、Gold、解析文档和 PDF 均留在仓库外；
- CLI stdout、`review_summary.md` 只输出数量、版本和状态，不输出论文内容；
- 构建器不会调用 Qwen，也不会用 Gold 调提示词或检索参数；
- `tuning_allowed=false` 和 `human_verified_gold` 由 Gold Schema 固定。

## 5. 定向测试

新增 `tests/unit/test_build_gold_dataset.py`，使用完全虚构的三题数据覆盖：

- `keep/edit/reject` 分别为 1 条，最终生成 2 条 Gold；
- edit 证据从文本块重算页码、block 顺序和两种 bbox；
- Review 中的 `gold_export` 与 resolution 同步；
- 冻结来源被修改或实际使用的 parsed document 未进入冻结清单时拒绝构建；
- 单人第二轮不足 24 小时时拒绝构建；
- 修订答案/证据不是所选 block 原文时拒绝构建；
- 已有生成文件且未显式允许替换时拒绝覆盖。
