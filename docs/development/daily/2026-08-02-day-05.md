## 2. 开始时的阻断问题

本日开始前确认了以下问题：

1. `deep_researcher.py` 的异常结束条件包含 `or True`，会无条件提前结束；
2. `asyncio.gather` 中一个并行 Researcher 异常可能影响整批结果；
3. 未知工具通过字典下标访问，可能直接触发 `KeyError`；
4. 只有报告文本和 `degraded` 推断，没有真正的 `success/partial/failed`；
5. Writer 可以在没有有效工具证据时继续生成看似完整的报告；
6. 没有 `src/scholarmind/` 和 Source—Evidence—Claim—Citation 模型；
7. 没有 PostgreSQL/pgvector Repository、批量向量索引、混合检索；
8. 没有 File Researcher 和 Claim–Evidence 发布门；
9. GitHub 仓库没有自动 CI；
10. 42 道 Silver 问题虽有完整标注手册，但缺少适合单人执行的每日批次。

Day 4 的直接回归目标是：8/8 报告当时都能生成文本，但 8/8 都是降级运行，
请求搜索 13 次、实际搜索 0 次。修复不能继续用“有 final_report 字符串”作为成功
标准。

## 3. 实现原则

- 保持上游图可导入，不重写整个 Open Deep Research；
- 失败必须成为数据，不能只存在异常日志中；
- 部分成功必须保留有效结果，同时公开失败原因；
- Writer 不信任单独的 `notes` 或计数，只信任可验证来源和哈希的证据记录；
- 本地文件报告只消费 `supported` Claim，拒绝 Claim 不得进入流畅文本；
- 论文开发/测试 split 在 Adapter 层再次强制隔离；
- 项目依赖继续只安装到 `.venv`，PostgreSQL 使用可选 extra 和独立 Compose；
- 没有实际运行过的能力必须明确标注，不用配置文件冒充运行验收。

## 4. Baseline 可靠性修复

### 4.1 移除无条件结束

删除 Supervisor 终止判断中的 `or True`。现在只有下列情况终止当前研究阶段：

- 达到迭代上限；
- Supervisor 没有产生工具调用；
- 明确调用 `ResearchComplete`。

终止时重新检查有效结构化证据；没有证据返回 `failed`，不能进入普通成功路径。

### 4.2 并行 Researcher 隔离

并行调用改用：

```python
await asyncio.gather(*research_tasks, return_exceptions=True)
```

每个返回值单独分类：

- 有有效证据：保留证据、压缩结果和成功计数；
- 抛异常：记录 `researcher_execution_failed` 或 Token 限制错误；
- 返回畸形对象：记录 `invalid_researcher_output`；
- 无可用证据：记录 `no_usable_research_output`。

一项成功、一项失败时整体为 `partial`；全部失败时为 `failed`。

### 4.3 未知工具与工具异常

Supervisor 和 Researcher 都不再用未经检查的 `tools_by_name[name]`。未知工具和
执行异常转换为 JSON Tool Error，包含 stage、code、message、recoverable、
tool name 和 tool call ID。错误 ToolMessage 会返回给模型用于后续决策，但不能被
算作证据。

### 4.4 三态状态和 Runner

主状态、Supervisor 状态、Researcher 状态和 Runner 增加：

- `research_status: success | partial | failed`；
- `research_errors`；
- `evidence_count`；
- 并行成功/失败单元计数。

Baseline 结果 Schema 同步允许 `partial`，同时保留历史 `report_error`。新增 Schema
回归测试验证历史 JSONL、结构化 partial、非法状态、缺少错误必填字段和多余错误
字段。

## 5. Writer 的结构化证据门

第一次实现只检查非空 notes，终审发现普通字符串仍可伪装证据，因此继续增加
`ResearchEvidence`：

| 字段 | 用途 |
| --- | --- |
| `source` | 区分普通工具与模型原生搜索 |
| `tool_name` | 实际产生观察结果的工具 |
| `tool_call_id` | 回到具体调用 |
| `content` | 原始成功观察结果 |
| `content_hash` | 正文 SHA-256 |
| `evidence_id` | 由来源、调用和哈希稳定生成 |

证据记录在 Researcher、Supervisor、Compression 和 Writer 之间逐层传递。每一层
重算正文哈希和稳定 ID，过滤重复记录、空结果和错误占位符。Writer 不再相信可被
单独伪造的 `evidence_count`：没有有效 `evidence_records` 时不配置、不调用报告
模型，直接返回 `failed/no_valid_evidence`。

Compression 失败但原工具证据仍有效时，透明回退原始证据并标记 `partial`；没有
结构化证据时拒绝压缩。

## 6. ScholarMind 领域模型

新增 `src/scholarmind/`，当前包含：

```text
adapters/      Baseline 与论文数据适配
config/        ScholarMind 前缀的项目配置
models/        Source、Evidence、Claim、Citation
researchers/   File Researcher
retrieval/     Dense、BM25、RRF、批量 Indexer
storage/       内存与 PostgreSQL/pgvector Repository
verification/  Claim–Evidence 第一阶段验证门
```

### 6.1 Source/Evidence/Claim/Citation

- Source：稳定 ID、来源类型、URI、内容哈希、paper/work 关系；
- Evidence：Source ID、逐字原文、页码/章节/bbox/chunk/block 定位；
- Claim：Evidence 多对多关系和五类验证状态；
- Citation：Claim—Evidence—Source—locator 的一致关系。

模型为 frozen Pydantic 对象，可 JSON 序列化。内存和 PostgreSQL Repository 都会
检查外键与 Citation 关系。

### 6.2 原文哈希修复

终审发现 `Evidence.create()` 若折叠段落换行，却继续保留 PR #5 chunk 的原始
`content_sha256`，会产生“字段哈希与实际正文不一致”。修复后 Evidence 只清理
首尾空白，保留内部换行；传入哈希时必须等于最终正文 SHA-256，否则拒绝导入。

### 6.3 split 防泄漏

`PaperDatasetAdapter` 默认只构建 `development` bundle，并要求 manifest 与 chunk
记录有相同 split。即使调用者误传全量 `chunks.jsonl`，`test` 记录也不会进入开发
索引。正式评测必须显式选择 `dataset_split="test"`。

## 7. PostgreSQL、pgvector 与检索

### 7.1 存储

新增幂等 SQL Schema：

- `CREATE EXTENSION vector`；
- Source、Evidence、Claim、Claim–Evidence、Citation；
- Evidence 全文索引；
- 按 embedding model 区分的 vector 表。

Repository 提供 CRUD、关系校验、embedding upsert 和 pgvector cosine search。
连接使用 autocommit，避免只读查询遗留 idle-in-transaction；失败语句不会把后续
操作永久留在 aborted transaction。

### 7.2 批量向量索引

Evidence Indexer 批量调用 `EmbeddingProvider.embed_documents`，检查返回数量、
维度、有限数值和模型名，再逐条写入 Repository。论文 bundle 可先 ingest Source/
Evidence，再调用同一 Indexer 建立向量。

### 7.3 检索

- `DenseRetriever`：provider-neutral 的余弦检索；
- `SparseRetriever`：确定性 BM25；
- `HybridRetriever`：加权 RRF；
- `PostgresDenseRetriever`：查询 embedding 后委托 pgvector 排序；
- `HashingEmbedder`：只用于零下载词法回退和测试，不宣称语义检索效果。

## 8. File Researcher 与验证门

File Researcher 执行：检索 → 页码 Evidence → Claim Draft → Verification → Citation
→ supported-only report。

第一次终审又发现两个假阳性/可靠性缺口：

1. 词集合覆盖会把 `A outperforms B` 与 `B outperforms A` 误判为支持；
2. 一个畸形 hit、Claim 或 Citation 异常仍可能中断整批。

本日继续修复：

- `supported` 必须能从某条已链接 Evidence 句子中严格抽取；
- 数字缺失/冲突、否定极性冲突仍单独判断；
- 多 Evidence 时优先选择真正包含原文的句子；
- 畸形 hit、Claim 创建、Verifier、状态转换和 Citation 按单 Claim 隔离；
- 仍有成功 Claim 时返回 `partial`，报告只包含 supported Claim；
- 全部失败、没有页码 Evidence 或没有 Citation 时 `report=None`。

严格抽取会拒绝合理同义改写。这是语义/NLI 验证器完成前的保守发布门，不是最终
语义验证能力。

## 11. 磁盘与安全

- 本次代码和测试不会下载新的大模型权重；
- Python postgres extra 的增量远小于模型权重；
- Docker image、数据库卷和未来 embeddings 会占用 Docker Desktop 数据磁盘；
- 若 C 盘紧张，应在大规模建库前把 Docker Desktop 数据磁盘放到 D 盘；

- CI 密码是一次性测试值，真实本地密码不进入 Git；
- `docker compose down` 保留卷，不能随手使用会删除数据的 `down -v`。
