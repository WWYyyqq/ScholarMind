## 2. 语义 Verifier 设计

### 2.1 两层发布门

新链路不是让大模型替代规则，而是组合两层判断：

```text
Claim + linked Evidence
        │
        ▼
确定性硬门：Evidence ID / 数字 / 极性
        │ hard fail ───────────────► 拒绝发布
        │ pass
        ▼
严格抽取式匹配 ── supported ─────► 直接发布，不调用模型
        │ lexical uncertainty
        ▼
Qwen JSON Schema 语义判断
        │ supported + confidence >= threshold + valid evidence indices
        ├──────────────────────────► 发布并生成 Citation
        └─ 其他 / 超时 / 非法输出 ─► 拒绝发布
```

数字矛盾、否定冲突、空 Evidence 或不存在的 Evidence ID 会设置
`hard_gate_passed=false`。语义模型没有覆盖权，避免模型用流畅解释绕过可确定的
事实错误。

### 2.2 结构化模型契约

本地 Qwen3-14B 通过 OpenAI-compatible `/v1/chat/completions` 返回：

- `label`：`supported|partial|contradicted|insufficient`；
- `confidence`：0～1；
- `reason`：简短判定理由；
- `supporting_indices`：1-based Evidence 下标。

请求使用 JSON Schema 限制字段和类型，代码再次执行严格解析：拒绝额外字段、
越界下标、布尔型伪数值，以及没有证据索引的 `supported`。Evidence 被明确标成
不可信数据，不能作为指令执行。

### 2.3 Fail-closed 与资源释放

- 语义置信度低于默认 0.75：降为 `partial`，不得发布；
- 模型超时、连接失败、空响应、JSON 错误：保留确定性结果并标记
  `semantic-fallback`，不得伪装成 supported；
- Service 正常关闭和组装异常均释放 Verifier HTTP Client；
- 默认 `verification_mode=deterministic`，无 GPU 的 CI 和开发环境仍可运行。

## 3. Service、CLI、API 与自检接入

新增项目变量：

```dotenv
SCHOLARMIND_VERIFICATION_MODE=semantic
SCHOLARMIND_VERIFIER_MODEL=qwen3-14b-local
SCHOLARMIND_VERIFIER_BASE_URL=http://[::1]:8000/v1
SCHOLARMIND_VERIFIER_API_KEY=local-not-required
SCHOLARMIND_VERIFIER_MINIMUM_CONFIDENCE=0.75
```

CLI：

```bash
.venv/bin/python -m scholarmind.cli research \
  "研究问题" \
  --retrieval-mode hybrid-rerank \
  --verification-mode semantic
```

LangGraph 输入增加 `verification_mode`，输出同时回显该模式。每条 Verification
增加 `confidence`、`verification_method` 和 `hard_gate_passed`，便于面试演示时
解释“哪个规则或模型作出了决定”。

`scholarmind doctor --verification-mode semantic` 不只检查端口健康；它要求模型对
安全合成的同义句返回结构化 `supported` 和有效 Evidence 索引，失败信息只包含
错误类型，不回显密钥或论文内容。

本地 LLM 启动脚本现支持 `SCHOLARMIND_VLLM_ENV`，因此不同 Git worktree 可以复用
同一个 ScholarMind 项目专用 vLLM 环境，而不复制约 7.6 GB 依赖或污染系统 Python。

## 4. 可重复 Verifier 评测

新增 8 条公开合成案例，覆盖：

- 严格抽取支持；
- 同义改写支持；
- 附加限定导致部分支持；
- 数字矛盾；
- 否定极性矛盾；
- `A outperforms B` / `B outperforms A` 关系反转；
- 无关证据；
- 两段 Evidence 联合支持。

确定性基线真实执行结果：

| 指标 | 结果 |
| --- | ---: |
| 案例数 | 8 |
| 分类准确率 | 62.50% |
| 发布精确率 | 100.00% |
| 发布召回率 | 33.33% |

它正确体现“安全但保守”：没有发布错误的支持项，但漏掉同义改写、多证据组合，
并把关系反转判为 partial。语义模式必须在同一文件上提升这些案例，同时保持数字
与极性硬门，才算有效增益。

运行命令：

```bash
.venv/bin/python scripts/evaluate_claim_verifier.py --mode deterministic
.venv/bin/python scripts/evaluate_claim_verifier.py --mode semantic
```

输出只含案例 ID、标签、置信度、方法和聚合指标，不包含私有论文。

## 5. Silver 人工复核工具

此前公开文档已经规定双轮协议，但冻结哈希、创建 42 个 ID 和分批仍需手工完成。
新增 `scripts/prepare_silver_review.py`：

1. 用正式 Silver Schema 校验每条记录；
2. 严格要求本次固定版本为 42 题（19 摘要、23 方法定位）；
3. 对配置、清单、test corpus、Silver 和全部解析文档计算 SHA-256；
4. 创建 5/12/13/12 四个批次；
5. 生成两轮顺序不同的 ID-only 队列；
6. 生成 42 份已绑定来源 ID 和输入哈希的空 Review 记录；
7. 目标目录存在时拒绝覆盖，保护已经填写的人工成果。

真实题目、答案、证据和论文仍留在原始私有数据集，GitHub 只提交工具、空模板和
流程。当前机器未找到原 `questions.silver.jsonl`，因此本日没有猜测或公开 4 条
争议题 ID，也没有伪造“已生成真实队列”的结论。找到原 `<DATASET_OUTPUT>` 后运行：

```bash
.venv/bin/python scripts/prepare_silver_review.py \
  --dataset "<DATASET_OUTPUT>" \
  --output "<ANNOTATION_ROOT>/paper-eval-v1"
```

### 6.3 Qwen3-14B-AWQ 冷启动与兼容性修复

真实首次启动暴露出两个仅靠 mock 无法发现的问题：

1. vLLM/ZeroMQ 把 IPC Socket 建在过深的 Git worktree 目录下，超过 Linux
   `sockaddr_un` 的 107 字节限制。启动脚本现默认使用
   `/tmp/scholarmind-llm-$UID`，也可用 `SCHOLARMIND_LLM_TMPDIR` 覆盖；
2. vLLM 0.26 的结构化输出后端不支持 JSON Schema 的 `uniqueItems`，请求会返回
   HTTP 400。请求 Schema 已移除该关键字，Python 解析器仍会去重并验证 Evidence
   下标，因此没有放松发布门。

修复后 Qwen3-14B-AWQ 真实启动成功：权重加载约 550 秒、首次
`torch.compile` 约 276 秒，整次冷启动约 15 分钟；模型占用约 9.44 GiB，连同 KV
Cache 和 CUDA Graph 后 GPU 总占用约 18.1 GiB。API 冒烟测试全部通过：

- 健康检查与模型发现；
- 普通 Chat Completion；
- JSON Schema 结构化输出；
- OpenAI-compatible Tool Call。

### 6.4 真实语义 Verifier 评测

首次评测的 5 个模型案例全部进入 `semantic-fallback`，根因正是上述
`uniqueItems` HTTP 400；该次结果不能作为 Qwen 效果指标。修复后先用一次直接
Provider 调用确认同义句被判为 `supported`，再运行完整固定集。

原合成案例 `cv-003` 同时写了“external hospitals”和“internal test set”，证据本身
明确反驳 Claim，却被预期为 `partial`。本次没有事后修改预期标签，而是把 Evidence
改成不带内外部冲突的“accuracy improves by 12%”，使案例只考察“额外适用范围没有
证据”这一单一能力。

最终同一 8 案例上的真实结果：

| 模式 | 准确率 | 发布精确率 | 发布召回率 | 耗时 |
| --- | ---: | ---: | ---: | ---: |
| Deterministic | 62.50% | 100.00% | 33.33% | 本地规则 |
| Qwen Semantic | 100.00% | 100.00% | 100.00% | 148.65 秒 |

语义模式 8/8：逐字支持走确定性快速路径；同义改写、多证据联合、关系反转和无关
证据由 Qwen 正确处理；数字和否定极性矛盾仍由硬门拒绝。这里是覆盖关键分支的
**8 条公开合成冒烟集**，只能证明实现和回归案例通过，不能替代 42 道 Silver →
Gold 的真实论文效果评测，也不能写成生产事实准确率。

### 6.5 Qwen Embedding 与完整运行栈

在 14B LLM 已占用 GPU 时并行启动 Qwen3-Embedding-0.6B，旧默认
`gpu-memory-utilization=0.15` 在 vLLM 0.26 下只能提供 0.41 GiB KV Cache，低于
4096 上下文所需的 0.44 GiB。将默认值实测调整为 0.18 后启动成功：模型约
1.12 GiB、KV Cache 约 1.53 GiB，可容纳约 14,320 tokens。LLM 0.75 与 Embedding
0.18 合计预留 7% 显存给驱动和波动。

真实 `doctor --verification-mode semantic` 返回 `ready=true`：

- PostgreSQL/pgvector：83 个 Source、10,881 条 Evidence、10,879 条向量；
- Embedding：1024 维响应正常；
- Reranker：语义排序检查通过；
- Semantic Verifier：结构化输出和 Evidence 下标检查通过；
- 总耗时：157.52 秒。

随后对私有论文库运行一次不回显正文的真实 CLI 端到端查询，结果为
`status=success`、`publication_ready=true`、5 条 Evidence、5 条 Claim、5 条
Citation、0 错误，耗时 155.10 秒。该路径的 Claim 是 Evidence 原句，因此 5 条均
被确定性快速路径验证，没有为逐字相同内容额外调用 Qwen；这验证了语义模式的
成本控制，而不是遗漏模型调用。
